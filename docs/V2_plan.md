# 空管智能助手 V2 — 完整业务闭环规划

> 2026-06-29
> V1 已完成技术验证（5 工具 Agent + RAG + DL）。V2 从业务闭环出发，面向真实空管运营场景。

## 用户画像

**核心用户**：空管管制员、流量管理人员、管制值班领导。

- 决策窗口短（几十秒到几分钟）
- 信息来自多个独立系统，紧急状态下切换慢
- 突发状况下最缺的不是原始数据，而是**影响评估 + 处置建议 + 通知清单**

## 价值量化：减少什么损失

### 1. 延误传导损失

一个小时的延误不是"一个小时的延误"。成都双流延误 30 分钟，连锁导致北京首都的下一个航段延误 45 分钟，再传导到上海浦东，三个航班、六百个旅客、机组超时、廊桥错位——

空管助手在**检测到异常的第一时间**就标出受影响航班和下游机场，管制员不是别人告诉他发生什么了才反应，而是**系统推给他**。反应每提前一分钟，传导链条就少一环。

| 场景 | 无系统 | 有系统 | 减少的损失 |
|------|--------|--------|-----------|
| 雷雨导致大面积延误 | 人工翻时刻表，逐个判断波及范围 | 系统立即列出受影响航班和下游机场 | 决策延迟从 10-15 分钟压缩到 < 1 分钟 |
| 跑道临时关闭 | 人工计算剩余容量 | 系统自动计算容量上限 + 建议盘旋上限 | 避免超容量放行导致复飞风险 |
| 军航禁飞 | 空域关闭后才知道影响范围 | 系统提前匹配受影响航班 + 替代航路 | 减少空中等待和备降 |

### 2. 容量浪费

跑道因为短时天气关闭了 40 分钟，恢复后头一个小时只放了 20 班——不是需求不够，是**没有人第一时间知道"现在可以放了"**。系统监控到流量恢复趋势后立即提示"容量已恢复，建议恢复正常放行速率"，每一个少放飞的时段都是白丢的起降时刻。

### 3. 决策失误的合规成本

管制员在紧急状态下凭经验处置，事后发现不合规——这不是能力问题，是人在几十秒内同时要考虑安全、效率、法规，信息过载了。系统把每条处置建议都附上法规条文，不只是"该做什么"，更是**"为什么可以这样做"**。事后复盘每一道决策都有法规依据可查。

### 4. 通知遗漏的协作断裂

大面积延误时该通知上级管制单位、相邻扇区、目的地机场、航空公司、管理局——漏一个就是协作断裂。系统自动生成通知清单，管制员只做确认，不做记忆。

### 5. 量化总结

| 损失类型 | 量化维度 | 预期改善 |
|---------|---------|---------|
| 传导延误 | 波及航班数 × 平均延误时长 | 提前 5-10 分钟启动措施，减少 30%+ 波及范围 |
| 容量浪费 | 恢复后未利用的起降时段 | 恢复信号不遗漏，利用率提升 |
| 决策合规 | 事后审查不合规事件 | 每条措施附法规依据，合规率接近 100% |
| 通知遗漏 | 漏通知导致的协作延迟 | 通知清单自动化，遗漏率降至 0 |
| 人员负荷 | 紧急状态下跨系统查询时间 | 一句话替代多界面切换，查询时间从分钟压缩到秒 |

## 信息输入：空管助手怎么"听到"问题

用户不是唯一的消息来源。系统同时从三条通道"听"：

### 通道 1：数据自动监控（不靠人报告）

```
流量时序数据 (flow_history 实时更新)
        │
        ▼
  Autoencoder 持续推理（每次推理：最近 24h 窗口）
        │
        ├── z-score > 2 → 异常触发 → 自动推送 Agent 评估
        │
        ├── 小时流量 > 机场容量 × 阈值 → 超容量预警
        │
        └── 计划流量 vs 实际流量 偏差 > 阈值 → 偏差告警
```

这一层不需要任何人开口。系统自己盯，自己判断，自己触发。

### 通道 2：外部系统对接（空管现有数据源）

| 数据源 | 信息 | 用途 |
|------|------|------|
| 空管自动化系统/雷达 | 飞机实时位置、高度、速度 | 判断实际空中流量 |
| 飞行计划库 | 计划时刻表（航班号、航路、机型） | 计划 vs 实际对比 |
| 气象系统 | METAR/TAF/SIGMET/气象雷达 | 天气异常关联判断 |
| 军航通告 | 临时禁飞区域、时段 | 受影响航班自动匹配 |
| 机场运控 | 跑道状态、停机位、除冰进度 | 容量变化实时更新 |

这些数据不是系统自己生成的——它们来自空管已有的信息系统。智能助手的作用是**把这些分散系统的数据汇总到一个决策上下文中**，省去管制员人工跨系统切换。

### 通道 3：管制员主动提问（自然语言）

```
"查一下成都双流受影响多少班"
"如果关闭 02L 跑道，容量掉到多少"
"给我备降机场建议，按容量排"
"生成大面积延误通知"
```

自然语言是**最后的输入通道**，不是唯一的。最好的系统是**你不开口它已经告诉你了**，开口只是追问细节。

### 总结：三通道输入模型

```
        ┌──────────────┐
        │ 数据自动监控  │ ← 不间断，秒级，被动触发
        │ (主要通道)    │
        └──────┬───────┘
               │
        ┌──────┴───────┐
        │ 外部系统对接  │ ← 持续性，提供上下文
        │ (数据来源)    │
        └──────┬───────┘
               │
        ┌──────┴───────┐
        │ 管制员主动提问 │ ← 按需，自然语言
        │ (交互通道)    │
        └──────────────┘
               │
               ▼
        ┌──────────────┐
        │  空管智能助手 │
        │  评估→建议→通知│
        └──────────────┘
```

## 完整业务闭环

```
检测 → 影响评估 → 处置建议 → 响应通知 → 事后复盘
```

### 阶段 0：检测触发（输入层）

系统持续监控流量数据。以何种方式触发智能助手介入：

| 触发方式 | 场景 |
|---------|------|
| Autoencoder 异常标红 | 流量模式与历史正常模式偏离 |
| 流量超容量预警 | 预计小时流量超过机场容量阈值 |
| 管制员主动提问 | 紧急状态下自然语言触发 |

### 阶段 1：影响评估

异常被触发后，系统自动分析并回答：

| 问题 | 评估内容 |
|------|---------|
| 影响范围多大？ | 涉及多少航班？哪些航空公司？ |
| 持续多久？ | 根据历史相似事件推断预计恢复时间 |
| 原因是什么？ | 天气/军航/设施故障/上游传导 |
| 传导效应 | 此次延误是否会波及下游机场？波及到什么程度？ |
| 严重等级 | 根据影响范围自动判定（一般/较大/重大） |

技术方案：
- 影响航班：Pandas 过滤当前受影响时段的航班数据
- 持续时间推断：规则引擎（按异常原因映射典型恢复时长）+ 历史相似事件查询
- 传导效应：基于航班联程数据预估下游延误
- 严重等级：按《民航大面积航班延误应急预案》标准自动化判定

### 阶段 2：处置建议

根据异常类型和严重等级，自动推荐处置措施，每条建议附法规依据：

| 异常类型 | 处置建议 | 法规依据 |
|----------|---------|---------|
| 雷雨覆盖机场 | 启动地面等待；建议备降机场（按航程和容量排序） | CCAR-93 第七条 |
| 跑道临时关闭 | 计算剩余跑道容量上限；建议空中盘旋架次上限 | CCAR-93 第五条 |
| 军航临时禁飞 | 列出受影响航班及替代航路 | CCAR-71 第七条 |
| 大面积延误 | 建议启动应急响应；通知上下游单位 | CCAR-121 第六条 |
| 预测流量超容量 | 提前 2 小时启动流量管理；安排地面等待 | CCAR-93 第七条 |

技术方案：
- 场景→措施映射：基于法规库构建规则库
- 备降机场推荐：按航程、当前容量、天气状况综合排序
- 替代航路：基于航路数据库自动计算（V2 暂不实现，文档中留接口）

### 阶段 3：响应通知

系统根据事件类型和影响范围，自动生成通知清单：

| 事件类型 | 通知对象 |
|----------|---------|
| 跑道关闭 | 塔台主管 → 进近管制 → 区域管制 → 受影响航司 AOC → 机场运控 |
| 大面积延误 | 上级管制单位 → 相邻扇区 → 目的地机场 → 各航空公司 → 管理局 |
| 军航活动 | 受影响航班机组 → 相邻管制单位 → 已审批航司 |
| 天气告警 | 进近/塔台 → 机场气象台 → 运控中心 |

技术方案：
- 通知规则库：事件类型 × 严重等级 → 通知范围
- 通知内容模板：自动填充受影响航班数、预计持续时间、建议措施等字段
- V2 目标：生成通知文本，人工确认后发送（实际对接通信系统在后续版本）

### 阶段 4：事后复盘

异常结束后，系统自动生成事件时间线：

```
检测时间 (T0) → 首次告警 (T0+N分钟) → 人工确认 (T1) → 
措施执行 (T2) → 流量开始恢复 (T3) → 恢复正常 (T4)
```

每步标注决策人、执行措施、效果。形成可归档的事件报告。

技术方案：
- 事件日志记录：Agent 工具调用链 + 人工确认节点
- 时间线可视化：Markdown 表格 + 关键指标变化
- 改进建议：比对历史同类事件，标注本次可优化环节

## 机载子系统：空地协同应急通道

地面端的智能助手解决"管制员怎么决策"。但飞机上发生的事，管制员不一定第一时间知道。机组在驾驶舱里面对故障、失压、医疗紧急情况时，最缺的是**地面即时支持**。

### 基本思路

在飞机驾驶舱（或电子飞行包/EFB 终端）部署一个轻量版智能助手，通过 ACARS/卫星数据链与地面端保持实时连接。当突发情况触发时，两端同时激活决策闭环。

### 机载端做什么

```
机载端（轻量，推理在本地或通过卫星链路到地面）
        │
        ├── ① 状态监测
        │   发动机参数异常、舱压低、航路偏离、
        │   燃油消耗异常速率——任何偏离正常包线的信号
        │
        ├── ② 自动告警 + 上下文打包
        │   不是发"紧急情况"四个字，
        │   而是打包：（当前位置 + 高度 + 速度 + 故障类型 +
        │             剩余油量 + 机上人数 + 最近的备降机场列表）
        │   一键发给地面端
        │
        ├── ③ 接收地面指令
        │   地面推送：最优备降机场排名、航路、预计到达时间、
        │   跑道状况、地面救援已通知
        │
        └── ④ 驾驶舱决策面板
            显示备降选项对比（航程/跑道长度/天气/医疗条件/地面保障）
            + 每项的预计飞行时间 + 剩余油量是否够
            机组做最终选择，系统确认后自动通知地面
```

### 地面端收到什么

```
机载端告警到达
        │
        ▼
  空管智能助手（地面端）
        │
        ├── 自动识别故障类型（引擎失效/客舱失压/医疗急救/...）
        ├── 匹配受影响空域（哪些航班需要避让？）
        ├── 计算备降方案（按航程→跑道长度→天气→医疗条件排序）
        ├── 自动通知：塔台 + 进近 + 消防/医疗/机场应急
        └── 向机组推送最优方案
```

### 空地协同的完整闭环

```
机载端检测故障
    → 自动打包上下文发给地面
    → 地面端收到，立即激活评估引擎
    → 地面生成备降方案 + 通知清单 + 空域调整
    → 推送回机载端
    → 机组确认方案
    → 地面收到确认，执行通知和空域调度
    → 飞机落地后，两端自动生成事件报告
```

全程**不需要机组和管制员打一个电话**。数据自己跑，人只做最后的确认。

### 场景举例

**引擎单发失效**：
1. 机载端检测到右侧发动机推力骤降 → 自动触发
2. 打包：位置 ZUUU 西 120 海里、高度 9800 米、右发失效、剩余油量 3.2 吨、机上 156 人
3. 地面端收到，3 秒内算出：最近备降机场 ZUCK（重庆江北）航程 28 分钟、跑道 3600 米、当前天气适航、机场有维修能力
4. 同时通知：重庆进近预留空域、重庆机场消防待命、航司 AOC
5. 机组在面板上看到 ZUCK 排第一，一键确认
6. 地面收到确认，自动引导航路，清理下方空域
7. 28 分钟后安全降落。完整事件报告已在两端生成。

**飞行中遭遇雷暴**：
1. 机载端通过气象雷达 + 地面对接气象数据，检测到前方航路有强雷暴云团
2. 打包：当前位置、雷暴范围、剩余油量、备选绕飞航路
3. 地面端收到，立即计算绕飞方案——向左偏航 30 海里绕过雷暴区，额外耗油 0.3 吨，仍在安全余量内
4. 同时检查绕飞航路是否与其他航班冲突、是否需要调整高度层
5. 推送绕飞建议到机载面板，机组确认后自动更新航路
6. 地面同步通知受影响扇区管制员：某某航班因雷暴绕飞，预计偏离原航路 8 分钟

**机上人员突发危重病情**：
1. 机组在 EFB 上选择"医疗紧急情况"类型，系统自动打包：位置 + 病人症状关键词 + 机上是否有医护人员
2. 地面端收到，立即筛选最近机场中**有机场急救站 + 最近三甲医院**的备降机场。不只看航程，还要看地面医疗条件
3. 地面自动通知：备降机场医疗急救中心待命 + 120 急救车到位 + 航司通知家属
4. 机组在面板上看备降选项对比：ZUCK（28min，有急救站但距三甲医院 40 分钟车程）vs ZUUU（35min，距华西医院 15 分钟车程）→ 选 ZUUU
5. 24 分钟后降落，医疗团队已在跑道待命

**机上安全威胁（劫机/暴力事件）**：
1. 机组触发隐蔽告警（不需要语音通话，避免刺激歹徒）→ 系统自动打包：位置 + 高度 + 机上人数 + 安全威胁类型
2. 地面端收到后进入"安全事件"模式——不通过语音频道回复，全部以文字/数据推送到驾驶舱
3. 地面立即通知：机场公安 + 反劫机中队 + 航司安保 + 管理局
4. 地面推送：最近可降落机场（优先军方协同保障的机场） + 预计到达时间
5. 若无合适备降场，地面计算空中等待方案，协调军方护航
6. 全程地面端不主动联系驾驶舱，等待机组下一步指令——机组知道地面已经全部准备好了，只需飞向目的地

### 场景分类与处置优先级

| 事件类型 | 检测方式 | 机载端动作 | 地面端动作 | 优先级 |
|---------|---------|-----------|-----------|--------|
| 硬件故障（引擎/舵面/起落架） | 飞机传感器数据异常 | 自动打包故障参数 + 飞行状态 | 计算备降方案，通知消防/维修 | 最高 |
| 天气威胁（雷暴/冰雹/风切变） | 机载雷达 + 地面气象数据 | 打包气象回波 + 当前位置 | 计算绕飞航路，协调空域 | 高 |
| 人员病情 | 机组触发 | 打包位置 + 症状 + 机上医护 | 筛选含医疗条件的备降机场 | 高 |
| 安全威胁 | 机组隐蔽触发 | 静默打包，不语音回复 | 进入安全模式，通知公安/军方 | 最高 |
| 燃油异常消耗 | 燃油流量传感器 | 打包消耗速率 + 剩余油量 | 计算最远续航，预设备降路线 | 中 |
| 客舱失压 | 舱压传感器 | 自动打包，触发紧急下降 | 立即清理下方空域 | 最高 |
| 鸟击 | 振动传感器 + 推力异常 | 自动打包受影响的发动机参数 | 计算单发备降方案 | 最高 |
| 起落架无法放下 | 起落架位置传感器 | 打包当前高度 + 油量 + 跑道长度需求 | 筛选超长跑道机场 + 地面消防泡沫待命 | 最高 |
| 货舱火警 | 货舱烟雾探测器 | 打包火警位置 + 当前高度 | 计算最近可用机场，通知机场消防 | 最高 |
| 机上危险品泄漏 | 机组触发 | 打包泄漏物质类型 + 机上人数 | 通知危险品处置专家 + 机场隔离机位 | 高 |
| 通信系统全失效 | 自动检测无线电静默 | 卫星链路自动切换 + 最后位置打包 | 按最后已知位置推算航线，清理预估空域 | 最高 |

### 技术约束

| 约束 | 当前方案 |
|------|---------|
| 机载端不能依赖云端 LLM | 机载端用本地小模型（如 Qwen2-7B 量化版 + 规则引擎）做故障识别和上下文打包，不做复杂推理 |
| 卫星链路带宽有限 | 机载端只发结构化数据包（JSON），不发语音/视频 |
| 机载端不能做复杂推理 | 备降方案排序、空域调整等复杂推理在地面端完成，机载端只做"显示+确认" |
| 安全冗余 | 机载端独立于地面端运行——即使链路中断，机载端仍有离线版故障检查单和备降机场数据库 |

### 与地面端的关系

机载子系统是地面端**输入通道的延伸**——在"三通道输入模型"中新增第四条通道。地面端原有的评估→建议→通知→复盘闭环不变，机载端提供的是一个**从驾驶舱直达决策引擎的数据入口**。

## 安全与可靠性设计

空管系统最基础的要求不是智能，是**不出错**。以下设计原则贯穿 V2 所有模块。

### 逐级确认机制

智能助手**不做自动执行**。每一条处置建议、每一个通知清单，都必须经过人工确认后才生效。

```
系统建议 → 管制员确认 → 系统执行
                ↓ 否决
          系统记录否决原因，不执行
```

告警可以自动触发，但行动永远是人说了算。

### 人机权限边界

| 系统可以自动做 | 必须人工确认 |
|-------------|------------|
| 流量异常检测与标红 | 启动大面积延误应急响应 |
| 影响航班清单计算 | 实际调整航班时刻 |
| 备降机场排序推荐 | 选择并确认备降方案 |
| 通知清单生成 | 通知消息实际发送 |
| 法规依据匹配 | 最终处置决策 |
| 事件日志记录 | 事件的定性 |

### 冗余与降级

| 故障场景 | 降级方案 |
|---------|---------|
| LLM API 超时/不可用 | 规则引擎兜底：预置的异常类型→措施映射仍可输出基础建议，只是没有自然语言润色 |
| 机载端卫星链路中断 | 机载端离线模式：本地故障检查单 + 离线备降机场数据库，机组可独立完成应急 |
| Chroma 向量库不可用 | 法规检索降级为关键词全文搜索 |
| DL 模型文件损坏 | 异常检测降级为简单阈值规则（流量 > 容量 × 1.2 → 告警） |
| 地面端电力中断 | 机载端自动切换至模式 C（独立运行），机组使用本地资源完成备降决策，链路恢复后自动同步事件记录 |
| 卫星链路拥塞（多机同时告警） | 按紧急等级排队，最高优先级（客舱失压/引擎失效/劫机）优先占用带宽，低优先级排队等候 |

### 多机并发应急

真实场景可能出现多架飞机同时遭遇同一危险天气或空域关闭。系统的并发处理：

```
同一空域内 3 架飞机同时遭遇雷暴
        │
        ▼
  地面端统一处理：
  ├── 为每架飞机独立计算绕飞方案
  ├── 检查三套方案之间是否冲突（航路交叉/高度层重叠）
  ├── 按燃油余量排紧急优先级（最少油量的先安排）
  ├── 统一调整空域：清理出安全通道
  └── 分别推送各机组的个性化方案
```

不会出现"三架飞机都收到同一个绕飞建议然后撞到一起"的情况。地面端有全局视角。

### 审计与追溯

- 每一次 Agent 工具调用记录入日志（工具名、参数、返回值、时间戳）
- 每一次人工确认/否决记录入日志
- 事件结束后生成完整决策链：检测→评估→建议→确认→执行→结果
- 日志格式标准化，可导入民航安全信息系统的审计流程
